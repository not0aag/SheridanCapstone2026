 SafeDrive AI - Project Summary & Scaling Guide
 Prepared 2026-07-22  |  Sheridan Capstone 2026  |  git branch: final-test
=====================================================================

SafeDrive AI turns any smartphone into a driver-safety co-pilot: the
front camera watches for drowsiness and distraction entirely on-device,
and alerts the driver within ~2 seconds with sound, haptics, and an
on-screen flash. Nothing is recorded and nothing leaves the phone.

---------------------------------------------------------------------
 PART A - WHAT WAS BUILT & FIXED
---------------------------------------------------------------------

1. BACKEND SECURITY & CORRECTNESS (FastAPI + SQLAlchemy)
   - Fixed a systemic authorization hole (IDOR): the trips, incidents,
     and videos endpoints had NO authentication - any request could
     read or modify any user's data by guessing an ID. All three were
     rewired to require a logged-in user and to scope every query by
     ownership, matching the pattern already used by the contacts and
     alerts endpoints (return 404, not 403, so resource IDs don't leak).
   - Upgraded password hashing from unsalted SHA-256 to bcrypt (the
     dependency was already declared but never wired in).
   - Added a 500 MB cap on video uploads and tightened error handling.
   - Test coverage grew from 10 to 39 tests (added users, trips,
     incidents, videos), all passing - including explicit cross-user
     "you cannot touch someone else's data" checks.

2. LOCAL DEV ENABLEMENT (on a locked-down, no-admin lab Mac)
   - The machine has no admin rights, so Homebrew/Postgres could not be
     installed. Workarounds: Python 3.11 via Miniconda (system Python
     was too old), and SQLite in place of Postgres for local runs (the
     data models use no Postgres-specific types, so it's a clean swap).
   - Backend boots end-to-end locally and the alert flow was verified.

3. TWILIO (SMS to trusted contacts)
   - Account SID and auth token are wired into backend/.env and were
     VERIFIED against Twilio's live API - authentication succeeds.
   - Only a purchased sending phone number is outstanding. Until that's
     bought, real SMS is intentionally deferred (see Part E).

4. iOS APP MADE FULLY STANDALONE (for the live demo)
   - The app previously needed a laptop-hosted backend on the same
     Wi-Fi for accounts and contacts - a real demo-day risk. It now
     runs 100% on-device: account and trusted-contact data persist
     locally (new LocalAccountStore + LocalContactsStore, following the
     app's existing on-device persistence pattern).
   - The entire networking layer and the backend are kept intact but
     dormant, so reconnecting later is a small, well-marked change -
     not a rebuild.
   - 44 iOS unit tests pass; the app builds cleanly and was launched on
     the simulator to confirm it runs.

5. CODE-QUALITY PASS (iOS)
   - Reviewed all 27 Swift files. The codebase was already strong
     (well-documented, correctly threaded, thoroughly tested), so the
     pass was deliberately surgical: removed an unsafe-looking force
     unwrap in the detection engine, documented the dormant networking
     layer so it isn't mistaken for dead code, and confirmed zero
     compiler warnings. No behavior changed; all 44 tests still pass.


---------------------------------------------------------------------
 PART B - HOW TO RUN IT LOCALLY
---------------------------------------------------------------------

iOS APP (the demo - needs nothing else running):
   1. Open ios/SafeDriveAI.xcodeproj in Xcode 16+.
   2. Select an iPhone 16 simulator (or a real device) and Run.
   3. Onboard -> Calibrate (~10s looking at the road) -> Start Monitoring.
   Everything (accounts, contacts, detection) works offline on-device.

BACKEND (only needed for the server-backed/scaled version):
   cd backend
   ./venv/bin/uvicorn app.main:app --reload      # http://localhost:8000
   ./venv/bin/pytest tests/ -v                   # 39 tests
   Config lives in backend/.env (gitignored). It currently uses SQLite
   and has USE_S3=false so no cloud accounts are required.

REGENERATING THE XCODE PROJECT (only if you add/remove Swift files):
   The .xcodeproj is committed and generated by XcodeGen from
   ios/project.yml. After adding files, run `xcodegen generate` in ios/.

 PART C - SCALING TO PRODUCTION (TECHNICAL PATH)
---------------------------------------------------------------------

The demo is a complete, self-contained product. To turn it into a
multi-user, cloud-backed service:

1. RECONNECT THE BACKEND (small, contained change)
   Flip three iOS call sites back from the local stores to the existing
   network client (APIClient.shared):
     - AccountManager           (login / register)
     - ContactsView / AddContactView   (trusted contacts)
     - DriverMonitor.sendDistractionAlert   (the SMS trigger)
   Recommended: keep the local stores as an OFFLINE CACHE so the app
   still works with no signal and syncs when back online (offline-first).

2. DEPLOY THE BACKEND
   - Host FastAPI + PostgreSQL on a managed platform (Render, Railway,
     Fly.io, or AWS). Move off local SQLite to Postgres.
   - Add database migrations (Alembic) - not present yet; today the
     schema is created directly. Needed for safe production upgrades.
   - Put the real HTTPS URL into the app's AppConfig; production builds
     already require HTTPS.
   - Turn on real S3 for the crash-video storage (already coded behind
     a USE_S3 flag; local disk is the current fallback).

3. TWILIO TO PRODUCTION
   - Buy a phone number or set up a Messaging Service, and leave trial
     mode. On a trial account, texts only go to pre-verified numbers.
   - Store contact numbers in E.164 format (+15551234567).
   - Consider carrier registration (A2P 10DLC) for reliable US delivery.

4. SHIP TO THE APP STORE
   - Signing/provisioning, App Store Connect listing.
   - Privacy nutrition labels for camera + location (the app already
     declares both usage strings and processes data on-device - a
     strong privacy story to lead with).
   - TestFlight beta, then review submission.

5. GO CROSS-PLATFORM & IMPROVE THE MODEL
   - An Android app already exists in the repo (app/, Kotlin/Compose) -
     finish and ship it to double the reachable market.
   - Fold in the model-training work under ml-models/ to push detection
     accuracy and reduce false alerts.
   - Add a web fleet dashboard for the B2B story in Part D.


---------------------------------------------------------------------
 PART D - SCALING AS A BUSINESS (VC PITCH ANGLES)
---------------------------------------------------------------------

PROBLEM: Distracted and drowsy driving kills thousands every year.
Existing fixes need costly hardware or ship your biometrics to the
cloud. SafeDrive AI needs neither - just the phone already on the dash.

MONETIZE (layered):
   - Freemium: free for personal drivers; paid Family/Pro tier adds
     trusted-contact alerts, trip history, and safety scores.
   - B2B fleet SaaS: per-seat/month for delivery, trucking, and
     rideshare fleets - dashboards, reporting, driver leaderboards.
   - Insurance partnerships: usage-based-insurance "safe driver"
     discounts; license the risk signal to insurers.

GET THE WORD OUT:
   - Direct to fleet operators, driving schools, and insurers (highest
     willingness to pay, clear ROI in avoided incidents).
   - App Store optimization + short-form social leaning on the privacy
     hook: "AI co-pilot that never sends your face anywhere."
   - Pilot programs with a local logistics/rideshare company for
     testimonials and real-world safety data.

PROJECT FUTURE (post-graduation):
   - iOS + Android from one detection core; a fleet web dashboard.
   - Better on-device models; expand to seatbelt/phone-in-hand cues.
   - Pursue road-safety grants and insurer pilots.

CALL TO ACTION (pick one to close the pitch):
   - "Download the beta and drive safer today."
   - "Join the waitlist / pilot program."
   - "Invest to help us bring this to every fleet."
   - "Fleet operator? Book a pilot with us."


---------------------------------------------------------------------
 PART E - HONEST STATUS / KNOWN GAPS
---------------------------------------------------------------------

- SMS is NOT sending yet. Twilio credentials are valid (verified live),
  but no sending number has been purchased, so the alert path currently
  fires the on-device sound/haptic/visual alert only. This is a
  one-setting change once a number is bought.
- The demo build is intentionally offline/local: accounts and contacts
  live on the phone, not a server. Multi-device sync needs Part C step 1.
- Local dev uses SQLite (lab-Mac constraint). Production must use
  Postgres + Alembic migrations.
- The Android app and the ML training pipeline exist but were out of
  scope for this pass; they are real next steps, not blockers.
- The on-device account password gate is a convenience lock, not a
  security boundary (there's no server in the demo). The real bcrypt +
  JWT auth already lives in the backend for the scaled version.
